## 建议清单

### 1. 文档引用资源库 —— 打通两个孤岛（价值高 · 成本中）

**缺口**：知识库与资源库是两套独立系统，文档里插不了图、引用不了模型文件。这是结构性的断裂，不是功能缺失。

**为什么值得做**：项目已有全部技术基础——预览管线（图片/模型/文本预览）、二维码分享（资源直链下载）、Markdown 净化渲染。只需：
- 编辑器里加资源选择器，插入 `![](/api/assets/files/<id>/preview/published)` 形式的引用
- 或用自定义语法 `![[资源名]]` 在渲染时解析

**参照**：Outline 等知识库均支持附件与文档互链；本项目的资源侧已有 published 指针，天然适合做「文档引用正式发布版」。

**风险**：文档里的资源链接在资源被删后会失效。需要决定是留占位符还是渲染时降级。

---

### 2. 搜索升级 FTS5 + 拼写容错（价值高 · 成本低）

**缺口**：`LIKE '%kw%'` 是全表扫描，且**子串匹配**——搜「部署」找不到「部属」，搜「git」会命中「digital」。

**为什么值得做**：
- SQLite 内置 FTS5，无需引入外部搜索服务（本项目是单文件 SQLite 部署）
- FTS5 支持 **BM25 相关性排序**（当前搜索结果只按 updated_at 排，命中度高的不一定靠前）
- 可用 `trigram` tokenizer 实现**中文子串 + 近似匹配**
- ARCHITECTURE 第 9 节早已把「搜索实现」列为待决策项，现在有数据支撑做这个决策了

**成本**：新增一个迁移建 FTS5 虚表 + 触发器同步，改造 `searchDocuments` 的 WHERE。约半天。

**注意**：FTS5 的 LIKE 语义与中文分词差异较大，需实测确认「部署」能命中「部属」。

---

### 3. 文档版本历史与回滚（价值高 · 成本中）

**缺口**：知识库侧**没有任何版本历史**。文档改错了只能靠手动改回来，误删直接丢失。

**为什么值得做**：资源侧已有成熟的版本模型（`asset_versions` + 最新/发布指针分离 + 恢复历史版本=复制内容生成新版本），**照搬即可**，是本项目内最省力的功能扩展。

**要做的**：
- 新增 `document_versions` 表（存每次保存的 title + content_md 快照）
- 编辑器加「历史版本」面板，可查看差异、回滚到任意版本
- 回滚语义与资源侧对齐：生成新版本而非倒退 latest

**参照**：ONES、Outline 等均把版本历史列为「五个关键能力」之一。

---

### 4. 资源去重与近似图合并（价值中 · 成本低）

**缺口**：`asset_versions.sha256` 字段已存在，但**没有任何查重逻辑**。同一张图换个文件名传两次，就占两份存储、占两条记录。

**为什么值得做**：
- **精确去重成本极低**：上传时算 sha256，命中已有记录就提示「该文件已存在（资源名，日期）」，让用户决定是复用还是新传
- **近似图合并价值更高但成本高**：需 pHash（感知哈希），sharp 已能算 dHash/aHash，配合 Hamming 距离判定。行业经验是**相似度只能提示不能自动合并**——两张不同照片可能有相近哈希

**参照**：Aprimo、PicaJet 都强调「精确去重用加密哈希，近似去重用感知哈希，两者缺一不可」，且**近似匹配只标记待人工确认，绝不自动删**。

**建议**：先做精确去重（半天），近似合并作为后续。

---

### 5. 统一备份覆盖资源库（价值高 · 成本中）

**缺口**：这是**数据保护漏洞**，不是功能增强。`exportSnapshot` 只导出文档数据，**资源文件（含原图、模型、预览图）完全不在备份里**。用户以为「备份了」，实际只备份了文字。

**为什么值得做**：
- 资源侧已有独立的 ZIP 导入导出（`asset-transfer.js`，流式读写 + 重新分配 id），**功能现成**
- 但知识库的 `/api/backup/export` 与资源库的 ZIP 导出是两条独立路径，用户要自己知道该导两次
- 应提供一个「全量备份」入口：文档快照 + 资源 ZIP 打包成一份，或至少在 UI 上明确提示「当前备份不含资源文件」

**这是最该优先修的**——一个让用户误以为数据已受保护的缺口，比十个新功能重要。

---

### 6. 补齐工具箱高频小工具（价值中 · 成本低）

**缺口**：工具箱只有 3 张卡片、1 个可用（比例锁定 480 行），json-fmt 与 qrcode 仍是空状态。

**调研发现的高频需求**（来自多个内网工具箱实践的共同结论）：
- **时间戳转换** —— Unix ↔ 日期、本地 ↔ UTC，带时区偏移
- **哈希计算** —— MD5/SHA1/SHA256，文件或文本
- **Base64 编解码** —— 含 URL-safe 变体
- **正则测试** —— 实时匹配、分组高亮
- **JSON 格式化/校验/路径查询** —— json-fmt 卡片已占位，但未实现
- **CRLF ↔ LF 转换** —— Windows/Unix 协作的高频小痛点
- **diff 对比** —— 两段文本差异高亮

**为什么这些适合本项目**：
- **纯前端计算，零后端依赖**，不碰数据与权限模型
- 可直接复用现有 `qrcode` 的动态 import 模式，避免打进主 chunk
- 顺带把 json-fmt / qrcode 两张「规划中」卡片落实，让工具箱不空

**取舍提醒**：调研中的实践共识是「**优先收录高频、稳定、算法固定的功能**，不要追求『几十种工具堆在一起』的数量目标，更值得追求『打开就有、用完就走、长期不坏』」。建议控制在 5~6 个高频项，不铺开。

## 明确不建议现在做的

| 方向 | 原因 |
|---|---|
| AI 自动标签 | 需引入模型依赖，与「受控内网、无外网」边界冲突；且本项目资源量级（几十个）用不上 |
| RBAC 权限系统 | 已是 F-SEC-001 延期特性。若要做应独立立项，不宜夹在功能迭代里 |
| 实时共同编辑 | 已是 F-COL-001 延期特性。技术上需要 CRDT 或 OT 方案，与现有乐观锁冲突 |
| 审批流 / 复杂工作流 | 调研共识：「增加贡献摩擦，反而杀死采纳率」 |
| 外部 CDN 集成 | 与受控内网部署假设冲突 |
| 端口扫描 / 网络工具 | 触发安全边界，且面向运维而非本项目目标用户 |

## 建议执行顺序

```
第 1 优先：统一备份覆盖资源库   ← 数据保护漏洞，不修是隐患
第 2 优先：搜索升级 FTS5          ← 成本最低、体验提升最直接
第 3 优先：文档版本历史与回滚     ← 照搬资源侧模型，最省力
第 4 优先：文档引用资源库         ← 打通孤岛，价值最大但要设计引用失效处理
第 5 优先：资源精确去重           ← 半天，锦上添花
第 6 优先：工具箱小工具补齐       ← 纯前端，顺手做
```

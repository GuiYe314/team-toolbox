- 配套：[DEVELOPMENT_PLAN](DEVELOPMENT_PLAN.md)（任务分解与阶段门槛）、[ARCHITECTURE](ARCHITECTURE.md)（技术约束与待决策清单）

## 1. 背景与范围

team-toolbox 是面向内部小团队的网页版工具集合。第一版（MVP）聚焦知识库：用 Markdown 文档沉淀团队知识，支持分类、标签、搜索与服务端持久化，首页展示最近更新。工具导航与卡片框架在本版落地，但**不实现任何具体小工具**。

**硬约束（适用于所有特性）**：

- C1 团队数据必须保存在服务端；禁止把浏览器 localStorage 当作团队共享数据库。
- C2 第一版无认证与权限，仅可在受控本机/内网环境运行；不得宣称无认证也能安全用于公网。
- C3 技术选型不依赖“最新版本”这一事实，具体栈由 TASK-001 决策（见 ARCHITECTURE 待决策清单）。

**版本范围**：

| 版本 | 范围 | 说明 |
|---|---|---|
| v0.1（MVP） | F-KB-001~008、F-NAV-001~002、F-OPS-001~002 | 完成门槛见 TASK-010 |
| 延期 | F-COL-001、F-SEC-001 | 单独标识，不计入 MVP 完成门槛 |

## 3. MVP 特性明细

每个特性按固定字段描述：价值与优先级 / 目标版本 / 前置与输入 / 流程与输出 / 失败与恢复 / 安全考量 / 验收标准（可测试）。

### F-KB-001 新建 Markdown 文档

- **价值与优先级**：P0。团队知识沉淀的最小入口，缺失则知识库不成立。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：进入“新建文档”页；输入标题（必填，去首尾空白后 1–100 字符）、正文（Markdown 文本，可为空，上限 1MB）、分类（可选，须为已存在分类）、标签（可选，每文档 ≤10 个）。
- **流程与输出**：提交 → 服务端校验 → 写入持久化存储并生成 id、version=1、created_at/updated_at → 前端跳转文档详情页并提示成功。
- **失败与恢复**：网络/服务错误时前端保留已输入内容（会话内草稿）并允许重试；校验失败返回字段级错误；服务端保证要么完整写入、要么不写入，不留半条数据。
- **安全考量**：正文按原文存储，仅在渲染时安全渲染（见 F-KB-002）；长度与结构在服务端校验。
- **验收标准**：1) 新建后列表与详情可见；2) 空/纯空白标题被拒并提示；3) 模拟断网保存失败后内容不丢失、重试可成功；4) 刷新页面与服务重启后文档仍存在（服务端持久化）。

### F-KB-002 编辑文档（含保存冲突处理）

- **价值与优先级**：P0。知识库的核心维护路径。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：已存在文档；编辑页加载标题/正文/分类/标签及当前 version。
- **流程与输出**：修改后保存并携带 version；服务端比对一致则写入、version+1、更新 updated_at；不一致返回 409 及服务端当前内容。编辑页提供与最终渲染一致的 Markdown 预览。
- **失败与恢复**：冲突时提示“文档已在别处被修改”，提供【加载最新（丢弃本地修改）】与【基于最新内容覆盖保存（需再次确认）】两个选项；MVP 不做自动合并。普通保存失败的重试策略同 F-KB-001。
- **安全考量**：Markdown 渲染必须安全渲染：默认转义 HTML、仅白名单语法可用，防止存储型 XSS。
- **验收标准**：1) 保存后详情页与首页 updated_at 变化；2) 两个会话先后保存同一文档，后者收到 409 与明确选项；3) 选“加载最新”后内容与服务端一致；4) 含 `<script>` 的 Markdown 保存后渲染不执行脚本。

### F-KB-003 删除文档

- **价值与优先级**：P0。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：已存在文档；删除入口位于文档页。
- **流程与输出**：点击删除 → 二次确认（显示文档标题）→ 服务端删除（含标签关联）→ 列表、搜索、最近更新均不再出现。
- **失败与恢复**：删除失败提示并可重试；确认框可取消。误删恢复走备份（F-OPS-002）；MVP 无回收站（回收站属后续增强，不承诺）。
- **安全考量**：二次确认防误触；接口仅接受已知文档 id。
- **验收标准**：1) 删除后列表/搜索/最近更新均不出现该文档；2) 取消确认则不删除；3) 与 F-OPS-002 联测：备份恢复演练可找回删除前内容。

### F-KB-004 分类管理

- **价值与优先级**：P1。横向组织文档。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：分类名称（1–30 字符，同级唯一）；MVP 仅一级分类、不嵌套、上限 50 个。
- **流程与输出**：新建/重命名/删除分类；重命名不影响文档归属；删除分类时其文档 category_id 置空（变为“未分类”），确认提示受影响文档数。
- **失败与恢复**：重名/超限返回明确错误；操作失败可重试。
- **安全考量**：名称服务端校验，渲染转义。
- **验收标准**：1) 新建/重命名后列表正确反映；2) 删除分类后原属文档显示“未分类”；3) 重名被拒并提示。

### F-KB-005 标签管理

- **价值与优先级**：P1。跨分类检索的轻量维度。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：编辑文档时输入标签名（1–30 字符）；保存时自动去空白、去重，英文字母统一小写合并。
- **流程与输出**：保存文档时同步文档-标签关联；列表页可按标签过滤（多个标签采用 AND 语义（同时包含所有所选标签），与分类筛选同时生效）；删除标签即解除全部关联。
- **失败与恢复**：超过单文档 10 个标签时提示；失败可重试。
- **安全考量**：名称服务端校验，渲染转义。
- **验收标准**：1) 添加/移除标签后正确显示；2) 重复标签自动合并；3) 按多个标签过滤仅返回同时包含全部所选标签的文档；4) 超过 10 个被拒。

### F-KB-006 搜索

- **价值与优先级**：P0。找回知识的主要手段。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：搜索框输入关键词（非空，去首尾空白）。
- **流程与输出**：服务端按标题+正文匹配（实现方式待决策：SQL LIKE 或轻量倒排索引，见 ARCHITECTURE），结果按 updated_at 倒序、分页返回，展示标题、摘要片段、分类、标签。
- **失败与恢复**：空关键词不发起查询；查询失败提示可重试；无结果显示空状态文案而非报错。
- **安全考量**：关键词须参数化/转义处理，防止注入（依存储技术实现）。
- **验收标准**：1) 命中标题或正文的文档出现在结果中；2) 无结果显示空状态提示；3) 结果按更新时间倒序；4) 特殊字符关键词不引发错误或注入。

- **实现方式（2026-10-23 更新）**：FTS5 全文索引 + 自研分词。
  - 分词：中文按 2-gram 切分（「部署指南」→ 部署 署指 指南），英文/数字按整词保留并转小写。
    原因：SQLite 内置的 unicode61 把连续 CJK 当成一个 token（搜「部署」命中不了「部署指南」），
    trigram 最短 3 字符（搜「部署」这类双字词无结果），ascii 只处理 ASCII。
  - 排序：BM25 相关性优先，相关度相同时按更新时间倒序。
  - 索引在应用层维护（写入/更新/删除文档时同步），服务启动时比对行数，漂移则自动重建。
  - 降级：若 SQLite 构建不含 FTS5，自动退回 LIKE 实现，搜索不中断。

### F-KB-007 服务端持久化

- **价值与优先级**：P0（支撑性）。没有服务端持久化就不是团队共享知识库。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：全部文档/分类/标签数据。
- **流程与输出**：写入部署机服务端存储（引擎确定为 SQLite；驱动与迁移方式由 TASK-001 决策）；支持导出为独立于引擎的备份格式（JSON 或 Markdown+元数据，见 F-OPS-002）。
- **失败与恢复**：存储写入失败返回错误且不破坏已有数据；服务重启后数据完整。
- **安全考量**：数据文件位于部署目录并最小化权限；数据与备份不进版本库（.gitignore 排除 data/、*.db、backups/ 等）。
- **验收标准**：1) 重启服务后数据保留；2) 导出文件包含全部文档与元数据；3) 团队成员在另一浏览器/设备可见相同数据（证明不是 localStorage）。

### F-KB-008 首页最近更新

- **价值与优先级**：P1。默认入口反映知识库活跃度。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：首页默认视图。
- **流程与输出**：按 updated_at 倒序展示最近更新的文档（标题、分类、标签、更新时间），默认 20 条，“查看更多”分页加载。
- **失败与恢复**：加载失败显示错误与重试；空库显示引导新建的空状态。
- **安全考量**：渲染转义。
- **验收标准**：1) 更新任一文档后其排到首位；2) 空库显示空状态；3) “查看更多”分页可用。

### F-KB-009 文档引用资源库

- **价值与优先级**：P1（打通知识库与资源库两个子系统）。
- **目标版本**：v0.2。
- **前置与输入**：资源库中的资源（Asset）；知识库文档正文（Markdown）。
- **流程与输出**：编辑器提供「插入资源」入口 → 弹窗列出资源（可搜索）→ 选中后
  在光标处插入**标准 Markdown 图片语法** `![资源名](/api/assets/files/<资产id>/<kind>/auto)`：
  - 图片类资源用 `preview`（缩略后的预览图，避免正文里塞几百 MB 的原图）；
  - 其他类型用 `original`（模型、纹理等本就要下载使用）。
- **版本语义**：pointer 用 `auto` —— 有发布版就用发布版，没有则退回最新版。
  资源一旦发布，文档里的引用自动跟进到正式版。
- **失效处理**：引用的资源被删除或文件丢失时，渲染为带 alt 文本的占位块
  （说明「引用的资源已删除或不可用」），而不是浏览器原生破图。
- **安全考量**：引用 URL 是同源相对路径，渲染仍走既有 sanitize-html 白名单，
  不引入新的 HTML 标签或协议。
- **验收标准**：1) 编辑器可选资源并插入引用，保存后正文含引用语法；
  2) 阅读页有效引用显示为图片；3) 失效引用显示占位块且保留原 alt 文本；
  4) 引用不削弱既有的 XSS 白名单与外链 rel 保护。

### F-NAV-001 工具导航与卡片框架

- **价值与优先级**：P1（框架性）。为后续小工具预留统一入口。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：工具清单配置（名称、一句话简介、状态=规划中）。
- **流程与输出**：首页/导航呈现“小工具”区块，卡片仅展示元信息，点击进入对应空状态页（F-NAV-002）。**本版不实现任何具体工具功能。**
- **失败与恢复**：无（静态框架）。
- **安全考量**：卡片文案渲染转义。
- **验收标准**：1) 至少 2 张示例卡片展示正确；2) 卡片状态明确标注“规划中”；3) 不包含任何实际工具功能或伪造的成功交互。

### F-NAV-002 工具空状态

- **价值与优先级**：P1。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：点击任一未实现工具卡片。
- **流程与输出**：统一空状态页：工具名 + “该工具尚未实现” + 返回工具箱入口；不向普通用户展示开发文档。
- **失败与恢复**：无。
- **安全考量**：无特殊项。

### F-KB-010 文档回收站

- **价值与优先级**：P0（数据保护）。与「备份不含资源文件」同类 —— 让用户以为自己有退路，实际没有。
- **目标版本**：v0.1（MVP 补充）。
- **前置与输入**：删除文档的操作（单条删除、批量删除）。
- **流程与输出**：
  - 删除 = **软删除**：只打 `is_deleted` 标记，**不物理删除数据**，子页面与标签关联全部保留。
  - 删除父页面时，整棵子树一并移入回收站（与旧版级联删除的可见行为一致）。
  - 知识库提供「回收站」入口（`/kb/trash`），列表按删除时间倒序，显示标题、分类、标签、
    正文摘要、删除时间、子页数。
  - 每条可「恢复」或「永久删除」；顶部可批量恢复、批量永久删除、清空回收站。
  - 恢复：连带整棵子树恢复，标签与正文完整带回，并重建全文索引（恢复后即可被搜索命中）。
  - 永久删除：物理移除，**必须二次确认**（接口要求 `confirm=1`），且**只允许删已在回收站里的文档**。
- **失败与恢复**：
  - 恢复时若上级页面已不存在或仍在回收站，该文档**自动提升为顶层**并在提示中告知用户，
    避免挂在一个看不见的父节点下成为孤儿。
  - 永久删除时，**已单独恢复正常的下层文档不受影响**（会被摘为顶层），
    不会被 `ON DELETE CASCADE` 连带删除。
  - 永久删除的影响面如实计入返回值（含随子树一起清掉的回收站文档），不虚报数量。
- **安全考量**：已删文档对正常列表、详情、搜索、页面树全部不可见，
  不可通过直链或接口绕过（详情报 404、编辑报 404）。
- **验收标准**：1) 删除后正常列表/详情/搜索/页面树均不可见，回收站可见；
  2) 恢复后正文、标签、可搜索性完整；3) 恢复时父级不可用则提升为顶层；
  4) 永久删除需二次确认且不带走已恢复的子页；5) 备份往返保留回收站内容与删除状态。

### F-AM-001 资源集合（Packs）

> 编号说明：资源管理子系统（TASK-010 起）此前未在本文档登记特性条目，
> 只在 DEVELOPMENT_PLAN 中有任务拆分。这是文档缺口，
> 补全整个资源管理的特性规格需要单独一轮梳理；本条目只登记 TASK-017 新增的能力，
> 不假装资源管理已完整覆盖。

- **价值与优先级**：P1（交付能力）。文件夹回答「归哪儿管」，集合回答「这次要交付哪些」。
- **目标版本**：v0.1（资源管理补充）。
- **前置与输入**：资源库中的资源（Asset）；用户对一组资源的临时编组需求。
- **流程与输出**：
  - 资源页提供「集合」入口；集合列表显示名称、描述、成员数、更新时间。
  - 可新建 / 重命名 / 删除集合，集合名唯一（重名给出可读提示而非数据库报错）。
  - 集合详情显示成员资源的缩略图、名称、类型、最新版本号。
  - 资源页批量操作提供「加入集合」：输入集合名，已存在则加入、不存在则自动创建。
  - 可从集合移除资源（多选），也可删除整个集合。
- **语义边界（最容易误解的地方）**：
  - 集合是**视图不是容器**：一个资源可同时属于多个集合；从集合移除或删除集合，
    **都不影响资源本身**、不影响它的文件夹归属、也不影响它所在的其他集合。
  - 集合与文件夹互补而非替代：文件夹是一棵树（一个资源只能待在一个位置），集合是多对多。
- **失败与恢复**：
  - 软删的资源不出现在集合里，从回收站恢复后**自动回到原集合**（无需额外维护成员关系）。
  - 资源永久删除时成员行由数据库级联清理，不留悬空引用。
  - 不能把回收站里的资源加进集合（会显示「3 个资源」但点进去只有 2 个）。
- **安全考量**：集合操作不涉及文件读写，只维护元数据关联。
- **验收标准**：1) 能建集合、加资源、看成员数；2) 一个资源可属多个集合；
  3) 重复加入幂等；4) 删集合不删资源、移出集合不删资源（界面对此有明确说明）；
  5) 软删资源离开集合、恢复后回到集合；6) 永久删除资源后成员行不悬空。

### F-OPS-001 受控内网访问边界

- **价值与优先级**：P0（边界性）。在无认证前提下这是唯一安全边界。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：部署配置（绑定地址/端口，经环境变量配置，样例见 env.example）。
- **流程与输出**：服务默认绑定内网/本机地址；README 与部署说明包含明确声明“仅限受控内网，禁止公网暴露”。
- **失败与恢复**：配置错误导致无法启动时给出可读错误提示。
- **安全考量**：本特性即安全边界本身；在 F-SEC-001 实现前系统无任何认证，公网暴露等于数据对公众可读写，必须杜绝。
- **验收标准**：1) 部署文档含边界声明；2) env.example 存在且 .env 被 .gitignore 排除；3) 默认绑定地址非公网通配，或文档对风险给出强制警告。

### F-OPS-002 备份与恢复

- **价值与优先级**：P0（数据安全）。
- **目标版本**：v0.1（MVP）。
- **前置与输入**：服务端存储中的全部数据。
- **流程与输出**：手动触发导出到 backups/（或配置的备份目录）；恢复按文档步骤导入备份重建数据；MVP 至少交付导出手段与恢复说明（由 TASK-009 实现）。
- **失败与恢复**：导出失败不损坏原数据；恢复前要求确认（恢复将覆盖当前数据）。
- **安全考量**：备份文件含全部团队数据，同样不进版本库，按内部资料保管。
- **验收标准**：1) 导出 → 清空 → 恢复后数据与导出前一致（演练一次并记录）；2) 恢复操作有覆盖确认。

#### 备份范围（2026-10-23 补充）

备份分两种范围，**界面必须明示区别** —— 此前只有「仅文档」一种，
用户点「导出备份」以为数据安全了，实际只保住文字：

| 范围 | 格式 | 含文档 | 含文档图片 | 含资源文件 |
|---|---|---|---|---|
| 全量备份 | ZIP | 是 | 是（`data/uploads/`） | 是（原图 / 预览图 / 缩略图） |
| 仅文档 | JSON / JSON.GZ | 是 | 否 | 否 |

- 全量备份为**流式**打包，不把大文件读进内存（资源可能是数百 MB 的 GLB）。
- 恢复为**合并模式**：不删除既有数据；文档按「同父级下同名」跳过，
  资源重新分配全部 id，同名文件夹跳过。恢复前需用户确认。
- 验收标准补充：3) 全量备份导出 → 清空 → 恢复后，**文档、图片、资源文件均与导出前一致**。

### F-OPS-003 自动更新

- **价值与优先级**：P1（降低「必须升级时没人升」的风险）。
- **目标版本**：v0.2。
- **前置与输入**：一个**可配置的更新源**（静态文件托管即可），其中包含
  `manifest.json` 与对应的发布包 ZIP。
- **流程与输出**：
  1. 「检查更新」读取 `manifest.json`，与本地版本比对；
  2. 「下载并安装」→ 下载包 → 校验 SHA256 → 解压 → **用包内自带的 node.exe 自检原生模块**；
  3. 通过后**先备份全部数据**，再由独立的 `apply.cmd` 在服务退出后换文件并重启；
  4. 新版本启动成功后清除 `pending` 标记；标记仍在则自动回滚到上一版。
- **更新源形态**：`http(s)://` 地址或本地/共享目录路径，二者行为一致。
  GitHub Releases、内网共享盘、nginx 目录、对象存储均可。**不绑定 GitHub** ——
  私有仓库匿名访问返回 404、未认证 API 限流 60 次/小时，这两条使其不适合作为唯一方案。
- **失败与恢复**：哈希不符 → 丢弃下载文件，不安装；包结构不全或自检不过 → 在动任何
  文件之前失败；换文件失败或新版本起不来 → 自动回滚，并留下 `ROLLBACK.txt` 供界面提示。
- **安全考量**：安装动作要求 `confirm=1`；包必须与清单声明的 SHA256 一致；
  解压防路径穿越；换文件**排除 `data/`**，用户数据永不参与替换。
- **验收标准**：1) 四种界面状态（未配置 / 已最新 / 有新版 / 清单损坏）均正确呈现；
  2) 哈希不符时不留下任何包文件；3) 包结构不全与自检失败均在动文件前被拒；
  4) 换文件后用户数据完好、新代码生效；5) 新版本未确认启动时自动回滚且数据完好。

## 4. 延期特性（不计入 MVP 完成门槛）

### F-COL-001 实时共同编辑（延期）

- 价值与优先级：P1（价值高但复杂度高，明确延期）。
- 目标版本：MVP 之后。
- 前置：MVP 与账号权限（TASK-D02）交付，且完成协同方案预研（TASK-D01）。
- 流程与输出（目标）：多人同时编辑同一文档，实时同步，冲突自动合并或低摩擦提示。
- 失败与恢复（目标）：断线重连后可同步；不可合并冲突回退人工决策。
- 安全考量（目标）：操作来源可识别（依赖账号体系方向）。
- 验收标准（目标，届时另行细化）：双端并发编辑最终一致。
- 说明：MVP 的乐观版本号（ARCHITECTURE 第 4 节）为其预留基础，但 MVP 不承诺任何协同能力。

### F-SEC-001 账号与权限（延期）

- 价值与优先级：P0（多角色/更开放部署的前提，但明确延期）。
- 目标版本：MVP 之后。
- 前置：MVP 交付且完成账号方案决策（TASK-D02）。
- 流程与输出（目标）：登录、登出、角色（如管理员/成员）、文档级权限。
- 失败与恢复（目标）：登录失败提示、会话过期处理。
- 安全考量（目标）：凭据安全存储与会话管理。
- 验收标准（目标，届时另行细化）：未登录/未授权访问被拒绝。
- 说明：在其实现之前系统只能运行于受控内网，任何场合不得宣称“无认证也可安全公网使用”。
